# 决策记录（ADR）

本文件记录这个项目里**不那么显然、且推翻了某个看似合理做法**的决策。
每条都写清楚：当时面对什么问题、选了什么、为什么、付出了什么代价、以及被否掉的备选。

阅读顺序建议：先看 ADR-001 / 002 理解整体形态，再看 005～012 理解内部结构。

---

## ADR-001 用自研轻量框架替代 AstrBot

**状态**：已采纳

**背景**
原方案是 AstrBot + SnowLuma 两个进程，在 1 核 2G 上常驻内存占用过高。
需求是"最小限度保留 QQ 机器人所需功能，其余全部移除"。

**决策**
不裁剪 AstrBot，而是重写一个只做四件事的 Go 程序：
收消息 → 判断该不该回 → 组上下文调模型 → 把回复发出去。
其余能力（面板、配置、会话、用量）围绕这四件事展开，不引入插件系统。

**理由**
- AstrBot 的开销大头是 Python 运行时 + 插件框架 + 依赖树，裁剪它等于和上游持续对抗，
  每次升级都要重新裁一遍。重写一次，之后没有这个负担。
- 功能边界被需求本身锁死了：QQ 私聊/群聊、@ 触发、上下文、LLM。这些用标准库 + 三个依赖就够。
- 单二进制在 1 核机器上的部署成本远低于 Python 环境。

**代价**
- 失去了 AstrBot 的生态（插件、多平台适配、现成的人格市场）。
  将来要接 Telegram / Discord，得自己写适配层。
- 这个项目从此是自己的维护负担，没有上游可以蹭修复。

**备选与否决理由**
- *裁剪 AstrBot*：改动面不可控，且每次上游升级都要重做。
- *换更轻的现成框架（如 NoneBot2）*：仍是 Python 运行时，内存收益有限。

## ADR-002 协议端仍然用 NapCat

**状态**：已采纳

**背景**
第一轮讨论中提出过"NapCat 封号风险太高"，考虑换其他协议端。

**决策**
继续用 NapCat（`mlikiowa/napcat-docker`），正向 WebSocket 模式。

**理由**
- 封号风险的来源是**协议实现方式**，不是框架。当前可用的、能稳定登录的方案
  在这一点上同源，换一个名字不会降低风险。
- 用户确认："风险同源则可以接受"。
- NapCat 有官方 Docker 镜像与清晰的 compose 示例，运维成本最低。

**代价**
- 仍然要扫码登录，仍然可能被风控。项目不对此做任何承诺或规避。

**补充事实（曾判断错误，已修正）**
早期从 SnowLuma 的部署经验带过来一个错误假设：NapCat 容器需要
`cap_add: SYS_PTRACE` 和 `security-opt seccomp=unconfined`。
查官方 README 后确认**不需要**——那是 SnowLuma 跑 Xvfb/x11vnc 的需求。
NapCat 只需要 `shm_size: 256m`（QQNT 底层是 Chromium，默认 64MB 的 /dev/shm 会崩渲染进程）。

## ADR-003 单二进制，前端用 embed 打进可执行文件

**状态**：已采纳

**决策**
`web/dist/` 通过 `//go:embed all:dist` 编进二进制，运行时从内存文件系统提供静态资源。

**理由**
- 交付物只有一个文件，不存在"忘了传 dist"这类故障。
- 部署时不需要额外的 nginx 或静态目录，容器镜像里只有二进制。
- 前端与后端版本天然对齐，不会出现旧前端打新接口。

**代价**
- 改一行 CSS 也要重新编译整个二进制。
- `web/dist/` **必须提交进 git**，不能像常规前端那样 gitignore。
  这条曾经踩过坑：`.gitignore` 里残留了 Vue 时代的 `web/dist/` 规则，
  导致服务器上 clone 后编译直接失败（`pattern all:dist: no matching files found`）。
  同理，`.dockerignore` 里写 `dist` 会匹配任意层级的同名目录，
  必须写成 `/dist`，否则 `web/dist` 会被一起排掉。

## ADR-004 前端不引入构建工具，手写原生 JS

**状态**：已采纳

**背景**
最初计划 Vue 3 + Vite。实际实现时改成了手写原生 JS（约 1500 行）。

**决策**
`web/dist/` 下三个文件：`index.html`、`style.css`、`app.js`，没有 npm、没有打包、没有 node_modules。

**理由**
- 面板一共 6 个页面，交互复杂度远低于需要框架的阈值。
- 引入 npm 工具链意味着：构建镜像要装 Node、CI 要多一步、1 核机器上多几分钟构建。
  这与"一键部署、单二进制"的核心承诺冲突。
- 没有构建步骤，改完刷新就生效，调试成本极低。

**代价**
- 没有组件复用、没有响应式系统、没有类型检查。页面再多几个就该换框架了。
- 事件绑定必须手写事件委托（CSP 禁内联 `onclick`，见下）。

**实现上的两个约束**
- CSP 是 `script-src 'self'`，所以**不能用内联 `onclick`**。
  全部走 `data-act` 属性 + 容器级事件委托。
- 每次路由切换必须换一个全新的 `<main>` 容器再挂监听器。
  否则监听器会跨页面累积，点一次触发 N 次（这个 bug 出现过）。

## ADR-005 配置分两层：TOML 管部署期，SQLite 管运行期

**状态**：已采纳

**决策**
- `etc/qqbot.toml`：数据目录、日志级别、OneBot 地址、面板监听地址。
  安装脚本生成，人工可改，**面板不写**。
- SQLite `settings` 表：LLM 配置、人格、触发规则、黑白名单。
  面板可写，改完立即生效。

**理由**
- 如果面板也写 TOML，人工加的注释会被冲掉，且并发写有竞态。
- 部署期参数（监听哪个端口）改了要重启，运行期参数（换个人格）不该重启。分开正好对应两种生命周期。

**代价**
- 两处配置，排查问题时要知道去哪看。`qqbot status` 与面板概览页都同时展示了两边。

## ADR-006 SQLite（纯 Go 驱动）+ WAL

**状态**：已采纳

**决策**
`modernc.org/sqlite`（纯 Go 实现），`journal_mode=WAL`、`synchronous=NORMAL`、`SetMaxOpenConns(4)`。

**理由**
- 纯 Go 驱动让 `CGO_ENABLED=0` 成立，产出的二进制可以扔进任意 Linux，不依赖 glibc 版本。
- 单进程、单写者、数据量小（会话 + 用量），SQLite 完全够用，不需要外部数据库。
- WAL 让面板读不被机器人写阻塞；`NORMAL` 在 WAL 下仍然崩溃安全，只是掉电可能丢最后一个事务——
  对聊天记录来说可以接受，换来的是每次写入不 fsync。

**代价**
- 备份不能直接热拷文件（WAL 里有未合并的数据）。`qqbot backup` 因此会先停容器再打包。

## ADR-007 认证：argon2id + TOTP + 双提交 CSRF

**状态**：已采纳

**决策**
- 密码哈希 argon2id（64MB / 3 轮 / 2 线程）。
- 可选 TOTP（RFC 6238），Secret 加密后存库。
- CSRF 用双提交：`qqbot_csrf` 是**非** HttpOnly 的 cookie，前端读出来放进 `X-CSRF-Token` 头，
  服务端比对两者。会话 cookie 是 HttpOnly + SameSite=Strict。
- 所有写操作（`PUT`/`POST`）都要求 CSRF 头；只读接口不要求。

**理由**
- 面板默认只监听 127.0.0.1，但用户可能自己反代出去，认证不能假设"外人进不来"。
- argon2id 是当前密码哈希的推荐选择；64MB 内存在 2G 机器上可接受（登录是低频操作）。
- 双提交 CSRF 不需要服务端存 token 表，实现简单且够用。

**代价**
- 登录时瞬时占用 64MB 内存。并发登录多了会顶到 `mem_limit`，但单用户场景不存在这个问题。

## ADR-008 LLM API Key 与 TOTP Secret 加密存储，密钥与库分离

**状态**：已采纳

**决策**
AES-256-GCM 加密，密文加 `enc:` 前缀存库。主密钥 `QQBOT_SECRET_KEY` 放在
`etc/env`（0600，root），**不进数据库**。

**理由**
- 数据库会被备份、会被 `qqbot backup` 打包、可能被误传。密钥单独存放，
  只拿到 `.db` 文件无法解密出 API Key。
- 前缀 `enc:` 让明文/密文可以共存：早期明文数据不需要迁移脚本，读取时按前缀判断。

**代价**
- 主密钥丢了 = API Key 全部要重新录入。启动时缺密钥会直接报错并给出修复提示，不会静默降级。

## ADR-009 日志：SSE 实时流 + 服务级轮转，不动 daemon.json

**状态**：已采纳

**决策**
- 面板日志页走 SSE（`/api/logs`），服务端设 `X-Accel-Buffering: no`，`WriteTimeout: 0`。
- 容器日志轮转写在 `compose.yaml` 的 `logging.options` 里（10MB × 3）。

**理由**
- **不改 `/etc/docker/daemon.json`**：那是全局配置，1Panel 会重写它。
  服务级配置零冲突，且随项目一起走。
- SSE 比 WebSocket 简单：单向、自动重连、走普通 HTTP，反代友好。

**代价**
- SSE 需要长连接，`WriteTimeout` 必须设为 0，否则连接会被定时切断。
- 反代时如果缓冲没关，日志会攒着不发。`X-Accel-Buffering: no` 是给 nginx 的提示。

## ADR-010 所有端口只绑 127.0.0.1，域名/证书/反代不在本项目范围内

**状态**：已采纳（范围经过一次收窄）

**背景**
最初计划包含 Cloudflare 证书申请与 OpenResty 反代模板。
用户明确："不需要给域名，域名是我手动进行反代的，跟这个项目没关系"。

**决策**
- `compose.yaml` 里所有端口映射到 `127.0.0.1`。
- 项目**不**生成证书、**不**提供反代配置、**不**假设有域名。
- 访问方式：SSH 隧道（`qqbot tunnel` 打印命令），或用户自己反代。

**理由**
- 反代是使用者的基础设施决策（用什么、证书怎么续、走不走 CDN），项目不该替他决定。
- 少一层反代 = 少一个故障点，也少一份要维护的模板。
- 绑定 127.0.0.1 是安全默认值：装完不会因为"忘了改密码"而被扫。

**代价**
- 想通过 `ip:端口` 直接访问面板，要显式 `--panel-bind 0.0.0.0` 重装。
  这是刻意的摩擦，不是缺陷。

## ADR-011 OneBot Token 默认留空

**状态**：已采纳

**背景**
最初 `install.sh` 会生成 `QQBOT_ONEBOT_TOKEN` 并注入两边。
实测查证 NapCat 官方文档后发现问题：`WEBUI_TOKEN` 与 `MODE` **只在配置缺失时初始化**，
`MODE=ws` 生成的 WebSocket 服务端**不带 token**。qqbot 侧带 token 去连，握手会 401。

**决策**
默认两边都不设 token。`qqbot.toml` 里 `access_token = ""`，
`install.sh` 不再生成 OneBot token。

**理由**
- 这是"装完就能用"与"多一道安全边界"的取舍。默认值必须让一键部署真的能跑通。
- 3001 端口只绑 127.0.0.1，同机进程才能连。在单租户 VPS 上（1Panel 本身就有 root shell）
  这个边界本来就是形式上的。

**代价**
- 想加固要手动：先在 NapCat WebUI 设好 Token，再把同一个值填进 `qqbot.toml`
  或 `etc/env` 的 `QQBOT_ONEBOT_TOKEN`，然后重启。文档里写了这条路径。

## ADR-012 容器内存配额与 uid 对齐

**状态**：已采纳

**决策**
- `napcat`：`mem_limit 1024m`、`mem_reservation 512m`、`shm_size 256m`、运行 uid 1000。
- `qqbot`：`mem_limit 256m`、`mem_reservation 64m`、运行 uid 10001。
- `install.sh` 在启动前 `chown` 两个数据目录到对应 uid。

**理由**
- 2G 机器上必须给系统和 1Panel 留余量，两个容器合计上限 1.25G 是算过的。
- **uid 不对齐是个隐蔽故障**：宿主目录由 root 创建（0755），容器内以 10001 运行，
  写 SQLite 时直接 permission denied，而报错发生在容器日志里，很容易被当成"启动慢"。

**代价**
- 换镜像（比如 NapCat 官方改了默认 uid）要同步改 `compose.yaml` 和 `install.sh` 两处。

## ADR-013 测试策略：mock 双端做端到端，race 上服务器跑

**状态**：已采纳

**决策**
- `internal/mock` 提供假的 OneBot 协议端（WS 服务端）与假的 OpenAI 兼容模型端。
- `internal/mock/integration_test.go` 组装**真的** store + 真的 bot.Engine + 真的 onebot.Client，
  只把两端换成假的，跑完整链路。
- `go test -race` 在服务器上跑（本地 Windows 无 gcc，`-race requires cgo`）。

**理由**
- 只测单元函数测不出"消息进来 → 判断 → 组上下文 → 调模型 → 分段发出"这条链路上的接缝问题。
- 假协议端能主动制造真实环境里难复现的情况：重复 message_id、连接断开、模型 500、发送失败。
- 这套 mock 立刻抓到了一个只会在真实环境暴露的 bug（见下）。

**代价**
- mock 本身要维护，且它的行为可能与真实 NapCat 有偏差。所以最终还是要在服务器上用真 NapCat 验一遍。

**顺带抓到的真实 bug**
`Event.PlainText()` 在消息只有 @ 段、没有文本段时，会回退到 `raw_message`，
而 NapCat 的 `raw_message` 是 CQ 码字符串，于是模型收到的用户消息变成了 `[CQ:at,qq=10001]`。
修复：解析成功但没有文本段时返回空串，只有 `message` 字段整体缺失才回退。

## ADR-014 安装目录布局

**状态**：已采纳

**决策**
```
/opt/qqbot/
├── compose.yaml        # 由 install.sh 从 deploy/ 拷入
├── etc/
│   ├── env             # 密钥（0600）
│   └── qqbot.toml      # 引导配置
├── src/                # 源码快照，docker build 的 context
├── data/
│   ├── qqbot/          # SQLite（uid 10001）
│   └── napcat/         # QQ 配置与登录态（uid 1000）
└── backup/             # qqbot backup 的产物，只留最近 7 份
```

**理由**
- `compose.yaml` 在根，`docker compose` 的相对路径（`./etc/env`、`./src`）自然成立。
- 源码放 `src/` 而不是直接铺在根，是为了让"要备份的东西"（`data`、`etc`）
  和"可以随时重建的东西"（`src`）在目录层面就分开。
- 升级 = 换 `src/` + 重建镜像；回滚 = 换镜像 tag。数据目录从不动。

**代价**
- 比"把 compose 放 deploy/ 里"多一层目录。换来的是一眼能看出哪个目录不能删。
